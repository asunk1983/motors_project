# Аудит UI/UX проекта "Паспорта двигателей"

## Общая информация
- **Дата аудита**: 02.08.2026
- **Контекст**: Внутренний рабочий инструмент для сотрудников промышленного предприятия — каталог паспортов электродвигателей
- **Аудитория**: Технический персонал (возможна работа с планшета/ноутбука в цеху)
- **Цель аудита**: Выявить функциональные проблемы UX/UI, мешающие работе

## Результаты аудита

### 1. Обратная связь при ошибках
**Статус: Требует внимания**

**Проблемы:**
- В `static/js/api.js` (строки 35-47) функция `request` обрабатывает HTTP-ответы и бросает `Error(data.error || resp.statusText)` — техническое сообщение.
- В `static/js/catalog.js`:
  - `loadEngines()` (строки 81-84, 94): ошибки отображаются через `showToast('❌ ' + data.error, 'error')` — передаёт текст ошибки, но не объясняет, что делать.
  - `updateStats()` (строка 18): пустой `.catch(() => {})` ошибки **проглатываются молча** — статус sidebar не обновляется, пользователь не видит, что что-то сломалось.
- В `static/js/engineCard.js`:
  - `showDetail()` (строка 58): `content.innerHTML = '<div class="no-data">Ошибка: ${e.message}</div>'` — технический текст ошибки внутри модалки, без подсказки.
  - `deleteCurrentEngine()` (строка 497): `showToast('❌ Ошибка: ' + e.message, 'error')` — тот же шаблон.
  - `saveDetailEdit()` (строка 459): `showToast('❌ Ошибка: ' + e.message, 'error')`.
  - `saveWorksOnly()` (строка 402): `showToast('❌ Ошибка: ' + e.message, 'error')`.
- Ошибки не стандартизированы: одни показывают `data.error`, другие `e.message`, третьи — `resp.statusText`. Пользователь видит набор из разных форматов технических текстов.

**Рекомендации:**
- Исключить пустые `.catch(() => {})` — хотя бы логировать в консоль.
- Стандартизировать обработку ошибок: toast с иконкой, кратким описанием и действием ("Повторить", "Обратиться в поддержку").
- Разделить технические детали (ошибки 500, 404) и пользовательские подсказки ("Сервер недоступен. Проверьте сеть и попробуйте снова").

### 2. Защита от разрушительных действий
**Статус: Критично**

**Проблемы:**
- **"Очистить БД"** в `templates/index.html`:
  - Строка 263: `onclick="clearAll()"` — кнопка "🗑 Очистить БД" на вкладке Импорт.
  - Строка 307: `onclick="clearAll()"` — кнопка "🗑 Очистить БД" в Настройках.
  - Функция `clearAll()` не найдена в `engines.js`, `catalog.js`, `engineCard.js` — вероятно определена в `static/js/app.js` или `static/js/backupManager.js` (файлы не просмотрены). Но по HTML — **никакого `confirm()` нет**.
  - Бэкенд (`routes/import_routes.py`, строки 196-215): `POST /api/clear` удаляет все двигатели, режимы, работы и **все фотографии с диска** (`shutil.rmtree(PHOTOS_FOLDER)` + `os.makedirs`). Это **полная потеря всех данных** — и базы, и фото.
- **Восстановление из бэкапа**: `static/js/api.js` строки 152-163 — `restoreBackup()` и `confirmRestore()` отправляют запрос без какого-либо диалога подтверждения на клиенте. Функция `clearAll()` (не найдена) скорее всего тоже не подтверждает.
- **Удаление двигателя**: `deleteCurrentEngine()` в `engineCard.js` (строка 483) использует `confirm()` — приемлемо для одного элемента, но текст подтверждения не указывает последствий.
- **Удаление фото**: `removeDetailPhoto()` в `engineCard.js` (строка 604) использует `confirm('Удалить это фото?')` — лаконично, но без указания, что фото будет удалено с сервера и этого нельзя отменить.

**Рекомендации:**
- Для "Очистить БД" и "Восстановить бэкап": двухэтапное подтверждение с вводом текста или чекбоксом "Я понимаю, что это удалит все данные".
- Либо отдельная модальная с подтверждающим полем ввода + объяснением последствий.

### 3. Состояния загрузки
**Статус: Требует внимания**

**Проблемы:**
- При загрузке списка двигателей (`loadEngines` в `catalog.js`): в `<tbody>` показывается текст "Загрузка данных..." (templates/index.html, строка 108) — но нет анимационного индикатора. При медленной сети пользователь не видит, что запрос ещё в процессе.
- При переключении между видами (таблица ↔ карточки) (`toggleView` в `catalog.js`): **нет индикатора загрузки** — пользователь видит пустой/перерисованный контент без обратной связи.
- `updateStats()` (`catalog.js`): при ошибке тихо падает, sidebar остается с нулевыми значениями — пользователь не видит, что статистика не загрузилась.
- Импорт (templates/index.html, строки 266-269): есть прогресс-бар — хорошая реализация.
- Создание/восстановление бэкапа: `backupManager.js` и `Api.createBackup()` не просмотрены. Но из `api.js` видно, что `createBackup()` возвращает `send_file` напрямую (binary), без прогресса загрузки.
- Экспорт (`exportSelected` в `catalog.js`, строка 342): `showToast('⏳ Подготовка экспорта...', 'info')` — toast исчезает через 3 секунды независимо от результата.
- Открытие детальной карточки (`showDetail` в `engineCard.js`, строки 27-28): показывается "⏳ Загрузка..." и "Загрузка данных..." — есть индикатор, но без анимации.
- Списки бэкапов и changelog/wishlist: в `index.html` строки 322, 382, 390 — статичный текст "Загрузка..." без анимации.

**Рекомендации:**
- Добавить CSS-спиннер (крутящийся круг) к существующему тексту загрузки.
- Для длительных операций (импорт, экспорт большого набора, создание бэкапа) — блокирующий оверлей с прогрессом.
- Для `updateStats()` — не молча падать, а показывать ошибку или индикатор загрузки в sidebar.

### 5. Читаемость данных
**Статус: Требует внимания**

**Проблемы:**
- Таблица двигателей (index.html строки 94-122): **8 колонок** (чекбокс, ID, место, тип, зав.ном., производитель, назначение, фото) — при ширине колонок `width: 50px`, `width: 36px`, `width: 70px` для ID/чекбокс/фото, а остальные растягиваются. На узком экране колонки сжимаются, текст переносится и становится непонятным.
- `font-size: var(--text-sm)` (12px) в таблице — меловато для цеха с плохим освещением.
- `.badge-id` (style.css строки 350-358): `font-size: var(--text-xs)` (11px), цвет `var(--color-text-muted)` (#6B7280) на фоне `var(--color-bg-main)` (#F3F4F6) — контраст ~1.5:1, **не читается вообще**. Бейдж ID практически невидим.
- `.photo-badge` (style.css строки 359-366): тот же `font-size: 11px`.
- `.info-chip` в карточках (style.css строки 415-425): `font-size: var(--text-xs)` (11px) для меток — `letter-spacing: 0.02em; text-transform: uppercase` — переводит в верхний регистр, что уменьшает читаемость.
- В детальной карточке `engineCard.js` (строки 128-145): `DETAIL_CHAR_FIELDS` выводит 15 полей в сетке `grid-template-columns: repeat(auto-fill, minmax(220px, 1fr))` — на планшете это может дать 1 колонку, прокручивая всё вниз.
- `detail-item label` (style.css строки 732-738): `font-size: 11px`, `text-transform: uppercase` — мало читаемо, особенно в цеху.
- Нет визуального выделения ключевых идентификаторов (зав. номер, тип) — все поля одинаковые.

**Рекомендации:**
- Увеличить базовый `font-size` для таблицы до 13-14px.
- Исправить контраст `.badge-id` и `.photo-badge` — либо увеличить цвет текста, либо поменять фон.
- Визуально выделить ключевые поля (зав. номер, место установки, тип) жирным или цветом.
- Добавить opooption "компактный/развёрнутый" режим для таблицы, чтобы скрывать редко используемые колонки.
- Оценить контраст через Lighthouse/axe-core.

### 6. Консистентность
**Статус: Требует внимания**

**Проблемы:**
- Смешанные подходы к обработчикам событий:
  - Инлайн-обработчики в HTML: `onclick="toggleView('table')"`, `onclick="refreshTable()"`, `onclick="showDetail(${e.id})"`
  - `addEventListener` в JS: `document.getElementById('sortSelect').addEventListener('change', ...)`, `document.getElementById('searchInput').addEventListener('input', ...)`
  - Инлайн-обработчики используются для простых действий, addEventListener — для сложных. Разделение нелогичное.
- Разные подходы к состоянию модальных окон:
  - `detailModal`, `photoAddModal`, `photoCropModal` используют `classList.add('active')`
  - `photoModal` использует `.photo-modal.active` (отдельный класс)
  - `login-overlay` использует `#login-overlay` (ID)
  - Состояние `body.modal-open` синхронизируется через `_syncModalOpenState()` — но не все модалки вызывают его при открытии (например, `showDetail` ставит `modal-open` напрямую).
- Кнопка "Очистить БД" есть на двух вкладках (Импорт и Настройки), но подтверждение (или его отсутствие) одинаково — это консистенция, но критичная проблема (см. пункт 2).
- Текст `confirm()` разный в каждой функции:
  - `confirm('Удалить двигатель ID=...')`
  - `confirm('Удалить запись №...')`
  - `confirm('Удалить это фото?')`
  - Нет единого шаблона.
- Иконки: смешаны эмодзи (📋, ➕, 🔍) и кнопки с именами классов. Где-то есть эмодзи в тексте кнопки, где-то — как отдельный `.tab-icon`.
- Toast-сообщения: часть с emoji префиксом (❌✅⚠️⏳), часть — без. Например, `showToast('✅ Работы сохранены')` vs `showToast('❌ Ошибка: ' + message)`.

**Рекомендации:**
- Единый шаблон для confirm: "⚠️ Действие необратимо. Продолжить?" с кнопками "Да, удалить" и "Отмена".
- Единый формат toast: `[emoji] Краткое сообщение` или `[emoji] Действие завершено: деталь`.
- Создать UI-компонент для модальных окон с единым API open/close и синхронизацией body.

### 7. Адаптивность
**Статус: Требует внимания**

**Проблемы:**
- CSS имеет `@media (max-width: 900px)` и `@media (max-width: 768px)` (style.css строки 1139-1159).
- При ширине ≤ 900px: sidebar превращается в горизонтальную полоску с `overflow-x: auto` — при 6 вкладках это удобно на планшете, но на телефоне кнопки сжимаются и становятся неразборчивыми.
- При ширине ≤ 768px: форма добавления становится 1-колоночной, модалка с `margin: 10px`, детальная карточка — 1 колонка. Хорошо.
- **Но** таблица двигателей при ширине ≤ 768px остаётся прокручиваемой по горизонтали (`overflow-x: auto` на `.table-wrapper`) — 8 колонок не помещаются, приходится горизонтально скроллить. Таблица — плохой выбор для мобильных.
- `.modal-content` имеет `max-width: 900px; width: 95%` — на экране 320px это даст ~304px ширины. Форма с 15 полями в одну колонку будет очень длинной.
- `.sidebar` фиксирована на 100vh (`height: 100vh; overflow: hidden`) — на мобильных браузерах адресная строка меняет высоту viewport, и `100vh` может выйти за экран. Использовать `height: 100dvh` (dynamic viewport units) или `height: calc(100vh - env(safe-area-inset-top))`.
- `.app-shell` тоже `height: 100vh` — аналогичная проблема.
- Нет `@media (max-width: 480px)` или `@media (max-width: 380px)` — для небольших телефонов стили 768px применяются как есть.

**Рекомендации:**
- Добавить breakpoint на 480px: уменьшить паддинги, увеличить кнопки до минимум 44x44px для touch.
- Использовать `100dvh` вместо `100vh`.
- Для таблицы на мобильных: скрывать колонки по умолчанию (оставлять только ключевые: тип, зав. номер, место), либо принудительно переключать на карточный вид.
- Добавить кнопку "скрыть/показать боковую панель" на планшетах.

### 8. Доступность/контраст
**Статус: Требует внимания**

**Проблемы:**
- **Контраст**:
  - `--color-text-muted: #6B7280` на белом — 4.8:1, проходит AA (но barely, для обычного текста).
  - `.badge-id`: `--color-text-muted` (#6B7280) на `--color-bg-main` (#F3F4F6) — контраст ~1.5:1, **не проходит минимум**.
  - `.sidebar-brand-text small`: `rgba(255,255,255,0.6)` на фиреневом фоне — контраст ~3:1.
  - `--color-warning: #B45309` на белом — ~4.5:1, borderline для AA.
- **Размер кликабельных зон**:
  - `.btn-sm`: padding `var(--space-1) var(--space-3)` = 4px 8px, `font-size: var(--text-xs)` (11px) — высота ~22px. **Меньше** рекомендуемых 44x44px для touch.
  - `.card-select` чекбоксы: 18x18px — слишком мало.
  - `.gallery-thumb-remove` / `.gallery-thumb-crop`: 22x22px — граница нижнего предела.
  - Но `.crop-handle::before` (style.css строки 604-608): `inset: -15px` растягивает hit-area до ~44px — **хорошее решение**.
- **Семантическая разметка**:
  - Нет `aria-label` на интерактивных элементах (кнопка удаления с `🗑`, чекбоксы без описаний).
  - Модальные окна управляются через `classList.add('active')`, но нет `aria-hidden` на скрытом контенте, нет `role="dialog"`.
  - Таблицы сортировки (`th.sortable onclick="sortTable(...)"`) — нет `aria-sort`, `role="button"` или `aria-label` для клавиатурных пользователей.
  - `:focus-visible` есть (style.css строки 93-96) — но только для элементов, которые его поддерживают. Некоторые элементы (кнопки с `onclick`) могут не получать фокус корректно.
- **Логика клавиатурной навигации**:
  - `engines.js` строки 140-181: обработчики клавиш стрелок и Escape для модальных окол — **хорошая** реализация.
  - Но `tabindex` на кликабельных строках таблицы (`tr.clickable-row`) отсутствует — нельзя фокусироваться через Tab на строку таблицы.
- **Предпочтения пользователя**:
  - `prefers-reduced-motion` есть (style.css строки 97-103) — хорошо.
  - `prefers-contrast` **нет** — не учитывается пользователи с повышенной потребностью в контрасте.

**Рекомендации:**
- Исправить контраст `.badge-id` и `.photo-badge` (сделать текст темнее).
- Добавить `aria-label` на все интерактивные элементы с иконками/эмодзи.
- Добавить `role="dialog" aria-modal="true"` и `aria-labelledby` на модальные окна.
- Добавить `tabindex="0"` и обработку Enter/Space на кликабельных строках таблицы.
- Добавить `@media (prefers-contrast: high)` для принудительного повышения контраста.
- Увеличить минимальный размер кнопок для touch-устройств.

## Приоритизация

**Критично (блокирует работу/риск потери данных):**
- Защита от разрушительных действий: очистка БД и восстановление бэкапа без подтверждения

**Высокий приоритет:**
- Адаптивность для планшетов и маленьких экранов

- Нет индикатора загрузки для длительных операций

**Средний приоритет:**
- Читаемость данных в таблице (мелкий шрифт, 8 колонок)
- Консистентность обработчиков событий и стилей подтверждений
- Пустые состояния без подсказок

## Вывод

Интерфейс имеет прочную функциональную основу, но требует доработки в ключевых областях, критически влиящих на безопасность данных и производительность работы в промышленной среде. Наиболее серьёзные риски связаны с отсутствием подтверждения разрушительных действий и плохой читаемостью при плохом освещении.
