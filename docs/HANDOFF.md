## Контекст сессии (обновлено)

Проект: Flask + SQLite + vanilla JS, промышленный учёт двигателей/оборудования/инцидентов. Прод — Ubuntu + gunicorn -w 4, разработка — Windows (Git Bash). Репозиторий-паттерн, без ORM.

Роли: архитектор (John) — тестирует, принимает решения; ревьюер (Claude) — пишет промты, проверяет diff'ы; исполнитель (джун, Cline-агент) — код-only, без доступа к запущенному серверу.

## Отложено (не забыть)

gunicorn --preload — фикс гонки воркеров при init_db() на проде (4 независимых процесса могут одновременно пытаться менять схему при restore/clear). Не протестирован: gunicorn принципиально не запускается на чистой Windows (нужны fork/fcntl из POSIX). Для честного локального теста нужен WSL или Docker — сейчас недоступны на машине разработки. Ждёт готовности такой среды.

equipment_placement — фича в разработке (многие-ко-многим оборудование↔место, схемные обозначения). В последней сессии не обсуждали конкретику — при следующем заходе нужно сначала уточнить у John, что именно осталось сделать по этой фиче.

## Рабочие правила (актуальные, дополнены/изменены с прошлой версии)

- Каждый промт джуну начинать с просьбы прочитать .clinerules.
- 1 шаг = 1 задание за раз, коротко, без объединения нескольких задач в один промт.
- Джун НЕ должен коммитить без явного "ок" от архитектора — были случаи самовольного коммита даже когда промт прямо просил сначала показать diff.
- Коммит-сообщения придумывает John (через Claude), не джун — задавать точный текст сообщения в промте, джун должен использовать его как есть, не переформулировать.
- Терминал — Git Bash (не PowerShell) на обеих машинах разработки. Раньше в PowerShell терялся первый символ кириллицы в git commit -m (проблема кодовой страницы консоли) — переключение на Git Bash решило эту проблему полностью.
- version.txt бампает джун, но только по явной команде в промте — не решает сам, когда версия достаточно "серьёзная" для бампа.
- У джуна нет инструмента "str_replace" — только editor(path, old_text, new_text). Он иногда теряет multiline old_text с тройными кавычками (сериализуется в null) — рабочий обход: одноразовый Python-скрипт с .replace() и проверкой count()==1 перед заменой, вместо прямого вызова editor.
- Для рискованных многострочных правок существующих файлов (не создание новых с нуля) в этой сессии Claude чаще сам вносил изменения напрямую (через точную построчную verification), а не поручал их джуну — после нескольких неудачных попыток джуна на автоматизированных regex-правках (случайно задевал соседний код). Стоит продолжать этот паттерн для сложных/крупных диффов, поручая джуну только разведку (чтение кода, поиск мест использования) и финальный коммит уже готового кода.
- Git-workflow между двумя ПК: коммит перед синком, pull перед началом работы, push после.
- sqlite3.exe не установлен на Windows-машине разработки — всегда Python-скрипты для SQLite.
